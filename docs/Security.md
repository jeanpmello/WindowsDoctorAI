# Segurança

**Estado:** controles e testes unitários descritos abaixo; não houve auditoria, certificação ou validação end-to-end em Windows, inclusive Windows Server 2019. Os scanners continuam somente de leitura. Nenhum plugin de reparo que altere o sistema está registrado.

## Controles atuais

- O manifesto permanece `asInvoker`; a aplicação não pede elevação administrativa.
- WMI, Registro e APIs Windows são acessados por adaptadores de leitura substituíveis.
- Knowledge JSON é dado declarativo, não código. Schemas 1.0 (compatibilidade), 1.1 (condição estrita) e 1.2 (provider estruturado allowlist) são limitados a 512 KiB/500 regras, rejeitam propriedades não mapeadas, limitam listas/texto, aceitam enum textual e referências HTTPS, e recusam caminhos absolutos, controles, scripts e padrões de comando/injeção. Regras estritas exigem código exato, scanner indicado e contexto específico no mesmo achado; no 1.2, providers requeridos devem ser identificadores canônicos conhecidos e são comparados ao campo estruturado, nunca ao texto da mensagem.
- Na tela inicial, a seleção de um arquivo JSON mostra versão, fonte declarada, SHA-256 e total de regras após validar schema/limites e antes de persistir. A Knowledge Base começa vazia; estado vazio é apresentado explicitamente. Pacotes inválidos ou conflitantes são recusados sem gravação parcial.
- Nenhuma DLL/script/plugin é descoberto a partir do JSON ou carregado de diretório. A origem textual e SHA-256 são metadados; SHA-256 não autentica o fornecedor. As URLs não são buscadas nem verificadas pelo app.
- `knowledge-packs/microsoft-windows-update-pilot.json` é uma curadoria de primeira parte a partir de duas páginas Microsoft. URLs e publisher declarado não equivalem a assinatura/autenticidade criptográfica; a UI continua sinalizando autoria não verificada. O arquivo é apenas disponibilizado para seleção: não é pré-carregado nem semeado no banco.
- As recomendações só existem quando há regra importada e match literal em achado coletado. A confiança informa força do match, não probabilidade de causa/sucesso; a fonte da regra continua não verificada automaticamente.
- Correlação compartilha identificadores observados e nunca declara causa determinada. Saúde/causa não é inferida a partir de indisponibilidade.
- Cada tentativa de reparo tem `RepairExecutionId` e registro local antes de chamar o plugin. O consentimento imutável identifica RepairId, versão, risco, alvo, ação e fingerprint do plano; confirmação booleana legada não autoriza ação. Recusas também ficam registradas. O plugin precisa aguardar o marco de início auditado antes de efeitos; falha ou cancelamento após o marco fica explícito como potencialmente parcial/inconclusivo. Se a gravação prévia falhar, o plugin não é chamado.
- Rollback requer o ID da execução original concluída com sucesso e consentimento separado para aquele rollback. A tentativa de rollback tem seu próprio ID e guarda o vínculo à origem; falhas e cancelamentos são auditados. A API legada de rollback sem ID não chama plugin.
- Pré/pós-condições e alvo no plano são metadados declarativos. O engine não consulta o estado do Windows e registra `NotEvaluated` quando não há verificador; um retorno bem-sucedido do plugin, sozinho, não comprova que o estado desejado foi alcançado. Exceções são registradas sem a mensagem interna, para reduzir exposição de dados.
- Scanners não usam shell arbitrário, não pedem elevação e não alteram serviços, Registro, arquivos, updates, drivers ou backups. A única consulta de processo desta fatia chama o `powershell.exe` existente por caminho absoluto, com `UseShellExecute=false`, `-NoProfile`, `-NonInteractive` e script fixo para `Get-WBBackupSet`; não aceita comando/argumento do usuário, não altera política de execução, não instala/ativa recursos e não invoca UAC. O runner tem timeout/limite de saída e descarta `stderr`; o plugin de demonstração permanece inerte.
- A saída da consulta de backup é limitada a status, contagem, data e um tipo normalizado (`Full`, `Incremental`, `Differential` ou `Other`). Nomes de máquina, destinos, caminhos e itens de backup não são solicitados pelo script, persistidos, registrados, exibidos na UI ou incluídos em HTML; campos extras em JSON são ignorados e texto bruto de erro/resposta não é propagado.
- O scanner só enumera metadados e não prova integridade, disponibilidade dos dados nem recuperabilidade. Segundo a [documentação Microsoft de `Get-WBBackupSet`](https://learn.microsoft.com/en-us/powershell/module/windowsserverbackup/get-wbbackupset?view=windowsserver2019-ps), a execução exige `Administrators` ou `Backup Operators`; acesso negado resulta em mensagem genérica e orientação para consultar o responsável, sem prompt de elevação ou alteração de permissões.
- O planejador `SyntheticFileRecoveryPreviewPlanner` é um modelo/serviço isolado, não registrado na UI nem conectado ao scanner: os itens aceitos vêm exclusivamente de uma lista sintética fornecida pelo chamador. Ele exige conjunto, versão, volume e item reconhecidos, origem e destino alternativo absolutos e distintos; rejeita campos ausentes/desconhecidos e qualquer solicitação de sobrescrita. A política do plano é fixa em `CreateCopy`, mas isso é apenas dado descritivo e não uma instrução executada. O planejador não consulta destino, permissões, backup ou filesystem e não renderiza comando copiável.
- A prévia não garante integridade ou recuperação e exige validação humana; não foi iniciada nenhuma ação. A documentação Microsoft de [`wbadmin start recovery`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/wbadmin-start-recovery) descreve `-recoveryTarget` e a opção `-overwrite:CreateCopy`; o aplicativo não invoca `wbadmin` nem `Start-WBFileRecovery`. Recuperação real aguarda validação própria em VM Windows Server 2019.
- Os testes Linux usam command runner falso e fixtures JSON sintéticas para sets presentes/ausentes, módulo indisponível, acesso negado, resposta inválida, timeout e falha, além de testes determinísticos do planejador sintético. Não constituem validação do Windows Server 2019 real. Nenhuma rota/scanner chama `wbadmin` ou comando mutador; `wbadmin start recovery`, `Start-WBFileRecovery` e qualquer restauração permanecem fora da implementação e exigiriam validação e autorização próprias.
- As duas orientações do piloto são manuais e exigem confirmação. `0xC1900107` recomenda reiniciar e repetir Setup; nada reinicia o computador automaticamente. `0x80073712` recomenda DISM elevado e modificador e, somente após sucesso do DISM, SFC; em falha de DISM, preservar/inspecionar CBS.log. Não há plugin real, execução de correção nem rollback documentado para essa sequência.
- Antes de exibir resultados ou persistir/exportar uma execução, `DiagnosticPrivacyRedactor` trata todos os campos textuais do resultado (`ScannerName`, `Category`, `Title`, `Description`, `Recommendation` e `Evidence`), inclusive dados de scanners/plugins e payloads legados. Também mascara identificadores conhecidos do inventário, endereços IP, e-mails, caminhos, GUIDs e atribuições comuns de credenciais. Nos eventos do `Event Viewer` e do `Windows Update`, remove o corpo da mensagem e conserva somente códigos HRESULT e metadados estruturados permitidos, como log, ID e nível. `SourceMetadata.Provider` só mantém nomes conhecidos de providers, normalizados para o identificador allowlist `WindowsUpdateClient`; providers arbitrários ou ausentes são omitidos. Esse campo permanece separado do texto redigido e pode ser usado pelo motor de regras. A seção de inventário da tela inicial usa `RedactInventory` antes de preencher a UI, tanto para diagnósticos novos quanto para registros carregados do histórico; essa cópia minimizada não altera a execução estruturada nem regrava payloads históricos.
- Redação e codificação HTML são etapas separadas: texto é minimizado primeiro e depois codificado com `WebUtility.HtmlEncode`. O formatter não carrega scripts, estilos ou imagens remotos; referências HTTPS declaradas só abrem por ação externa do usuário.
- Novas gravações SQLite armazenam a cópia redigida; payloads anteriores não são reescritos nem apagados. Ao carregar uma execução legada, o inventário da tela inicial e os resultados apresentados na área de achados são redigidos para exibição; qualquer novo HTML também redige payloads antigos sem alterar a linha original. A sanitização cobre padrões conhecidos, mas não prova a ausência de todo segredo arbitrário em texto declarativo/importado; não inserir credenciais e revisar o conteúdo antes de compartilhar.
- **Salvar diagnósticos no histórico** é opt-in e começa desligado. A migração de schema 4 volta a desligar essa preferência em instalações existentes sem apagar as execuções salvas; o usuário precisa marcar e salvar para autorizar novas gravações.
- Retenção por idade continua separada do opt-in de gravação e conserva por padrão (`0` dias). A UI oferece 30, 90, 180 ou 365 dias e mostra uma confirmação explícita, com o prazo e o efeito, antes de salvar uma preferência que possa expurgar registros. Cancelar não salva a preferência nem altera linhas. O aplicativo não expurga por idade ao iniciar; um expurgo só ocorre após confirmação no fluxo de salvar configurações.
- **Apagar todo o histórico de diagnósticos** exige confirmação e remove, em transação, apenas linhas de `DiagnosticRuns`. Não remove arquivos HTML exportados, histórico de reparos, preferências, regras ou pacotes. A exclusão SQLite é lógica, não sobrescrita segura; SQLite não fornece criptografia em repouso.

## Revisão e confiança dos pacotes

O schema evita campos para comandos, caminhos ou executáveis e rejeita campos desconhecidos. O conteúdo não é interpretado como código nem executa comandos; textos com padrões comuns de comando/injeção são recusados. Isso reduz superfície de execução, mas não torna verdadeiras as afirmações importadas: um arquivo ainda pode conter conteúdo enganoso, referências sem relação ou impacto incorreto. A prévia e o hash não comprovam autoria, assinatura, reputação ou veracidade. Revise origem, versão, regras e URLs antes da importação. A validação do domínio HTTPS não verifica autenticidade, disponibilidade ou conteúdo da página. Para o piloto, o termo “curadoria de primeira parte” descreve a seleção editorial das páginas Microsoft citadas, não uma atestação criptográfica da origem do arquivo.

A interface permite salvar o relatório HTML no destino escolhido pelo usuário, a partir da execução atual ou mais recente carregada. O relatório inclui resultados e evidências disponíveis e recomendações que correspondam a regras importadas. Não agrega `RepairHistory`: não há vínculo confiável entre esses registros e a execução diagnóstica atual; a trilha de auditoria permanece no SQLite e não é apagada. Textos de resultados, correlações, regras e recomendações passam por minimização antes do encoding HTML; códigos de erro e metadados úteis são mantidos. `High` representa força de correspondência literal, nunca probabilidade causal ou de sucesso. Revise o arquivo local antes de compartilhar.

Arquivos HTML escolhidos e exportados pelo usuário ficam fora do banco e da política de retenção. A aplicação não os apaga automaticamente — inclusive os relatórios pré-existentes — e a geração de relatórios futuros não altera arquivos já salvos.

## Dados locais

Com histórico ligado, SQLite grava resultados locais minimizados, removendo identificadores explícitos, campos livres de disco/rede, padrões comuns de dados pessoais e corpos de mensagens de eventos. Registros anteriores à redação continuam intactos no banco; exibição de achados e exportações HTML aplicam redação também a eles. Dados não são enviados a serviços externos neste milestone. SQLite não fornece criptografia em repouso nem apagamento físico seguro. Desligar o histórico não remove dados; retenção conserva por padrão e todo expurgo por idade exige confirmação visível.

## Próximos controles antes de reparos reais ou Enterprise

- Para cada reparo real: pré-condições e verificadores efetivos de pós-condições, alvo/alcance, privilégios mínimos, risco, plano de restauração quando viável, aprovação separada e vinculada por ação, tratamento de interrupção/parcialidade e testes em Windows isolado. Os contratos desta fatia não suprem essas validações.
- Para importar conhecimento: assinatura/proveniência verificável, processo de revisão e critérios de confiança/impacto antes de distribuir pacotes oficiais; a prévia e o hash atuais não autenticam autoria.
- Para relatórios: revisar textos declarativos arbitrários e garantir compartilhamento deliberado; a minimização dos campos conhecidos, retenção configurável e exclusão confirmada estão implementadas localmente.
- Para Enterprise: autenticação, autorização, isolamento de tenants, transporte, inventário central, retenção, auditoria, resposta a incidentes e consentimento devem ter desenho próprio. Nada disso é fornecido pelo Core atual.
- Revisar dependências, threat model e APIs Windows antes de releases. Testar contas padrão e hardware/firmware distintos.
